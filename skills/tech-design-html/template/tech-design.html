Webhook delivery: tech design

Draft for review by the Platform and Infra teams · Author Name · 1 January 2030 · follows the kickoff notes. Names, schemas and endpoints are proposals unless §2 marks them agreed. Every name and number on this page is a made-up example.
Summary
  1. One delivery service for every team. Teams publish an event once. The service delivers it to every subscriber's URL, signs it, and retries it. No team writes its own retry loop again.
  2. At-least-once, never lost. An event is saved before it is accepted, and every attempt is saved before it is sent. Subscribers dedupe on eventId.
  3. Two layers. The Platform team owns subscriptions, signing and the console. Infra owns the worker pool and the queue.
  4. First step: move the billing webhooks. Done when they run on the service with no lost deliveries over a release.

Non-goals

4The subscription

A subscription is a definition, not code. Both examples are illustrative.

Simple · all events 
# billing/subscriptions/partner-a.yaml
key: billing.partner-a
owner: { team: billing }
url: https://partner-a.example/hooks
events: ["invoice.*"]
retry: { max: 10, backoff: exponential }
Filtered · ordered 
# orders/subscriptions/warehouse.yaml
key: orders.warehouse
owner: { team: orders }
url: https://wh.example/orders
events: ["order.shipped"]
ordering: per-key        # key = orderId
retry: { max: 20, backoff: exponential }

FieldMeaningValidated at publish

orderingnone or per-key.The key is in the schema

8Security and reliability

On every delivery, in order
  1. Resolve the subscription and its secret.
  2. Sign the body with HMAC-SHA256.
  3. Send through the egress proxy.
Secrets

Per-subscriber secrets, rotated with an overlap window. Workers never log payloads.

A worker crashes after sending

One-line takeaway: a crash can repeat a delivery, never lose one; subscribers dedupe on eventId.
